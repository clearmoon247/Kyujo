# Port patches

Generated by `tools/native/patch_index.py` from the heads of `port/patches/*.patch`; edit the patch head, not this file.

The decomp itself is never modified: `tools/native/srctree.py` copies it and applies these patches in order, and the native build compiles the copy. Each patch states what it changes and WHY.


## 0001-rcp-io-macros.patch

Port patch 0001 - route RCP register access through the host
Why: IO_READ/IO_WRITE dereference KSEG1 addresses (0xA4000000...). Natively those are unmapped. libultra's C code uses these
two macros for every device register, so redirecting them lets the real libultra run on an emulated register file.

Files: `lib/ultralib/include/PR/rcp.h`


## 0002-ultralib-stdarg.patch

Port patch 0002 - stdarg.h for non-IDO compilers in the bundled libultra
Why: lib/ultralib/include/ido/stdarg.h uses __builtin_classof, which only IDO has. The game's own include/stdarg.h already
falls back to the compiler builtins when __sgi is not defined; this does the same for the library copy.

Files: `lib/ultralib/include/ido/stdarg.h`


## 0003-destroythread-hook.patch

Port patch 0003 - tell the host scheduler when a thread is destroyed
Why: each N64 thread runs on a host thread (src/ultra/os_sched.c). When osDestroyThread removes a thread, its host thread must stop
being a scheduling target; the hook is called after the thread is off every queue and before the next thread is chosen.

Files: `lib/ultralib/src/os/destroythread.c`


## 0004-idle-loop.patch

Port patch 0004 - host idle in the idle thread
Why: Idle_ThreadEntry ends in an empty endless loop that the console's interrupts preempt. A host thread cannot be preempted by
an N64 interrupt, so the loop waits for a hardware event and delivers it (HostIdle in src/ultra/os_sched.c).

Files: `src/main.c`


## 0005-initialize-no-exception-vectors.patch

Port patch 0005 - osInitialize without the exception-vector copy
Why: osInitialize writes MIPS handler code to the CPU exception vectors at 0x80000000.., which do not exist on a PC (a write there
would crash). The scheduler layer handles interrupts instead (src/ultra/os_sched.c).

Files: `lib/ultralib/src/os/initialize.c`


## 0006-main-pool-end.patch

Port patch 0006 - main memory pool end as a host pointer
Why: Util_InitMainPools passes POOL_END_4MB / POOL_END_6MB (0x80400000 / 0x80600000, N64 addresses) as the end of the pool whose start
is the host array gPool. The end must be gPool plus the same size. POOL_START is the N64 address gPool was linked at (include/variables.h).

Files: `src/util.c`


## 0007-game-direct-hw-access.patch

Port patch 0007 - the game's direct hardware accesses
Why: the game (not libultra) touches hardware in a few places without the IO_READ macro:
  - HW_REG() in include/macros.h dereferences 0xA4xxxxxx. Natively that is not memory. Every use that gets executed now stops the
    program and names the register; the two uses that the game really reaches are changed to IO_READ (below).
  - src/game_state.c (Game_DoCopyProtection) and src/fragments/area_select (AreaSelect_CheckCartRemoved) read a word of cartridge
    space (0xB0000E38, 0xB0000D10) to detect a removed or non-original cartridge. IO_READ serves it from the loaded ROM.
  - src/libleo/driveexist.c (LeoDriveExist): report "no 64DD drive" instead of probing the drive's ROM over the PI bus. The 64DD
    is not emulated; a console without the drive gives the same answer.

Files: `include/macros.h`, `src/game_state.c`, `src/fragments/area_select/area_select.c`, `src/libleo/driveexist.c`


## 0008-native-addresses-and-ai-length.patch

Port patch 0008 - native addresses are their own "KSEG0" addresses
Why: on the console a physical address and its virtual (KSEG0) address differ by 0x80000000, and the game converts between them with
that constant. In this port a pointer IS the address the emulated hardware uses (src/ultra/os_memmap.c: osVirtualToPhysical is the
identity), so adding 0x80000000 would turn a valid pointer into one that cannot be dereferenced.
  - src/util.c Util_ConvertAddrToVirtAddr: the "physical address" branch returns the address unchanged instead of OR-ing in 0x80000000.
  - src/stage_loader.c: segment 0 ("physical memory", used by display lists) is based at 0 instead of 0x80000000, so the display-list
    word for segment 0 is the plain address, as osVirtualToPhysical would give.
  - src/3D140.c Audio_CreateFrameTask: reads the audio length register through IO_READ (HW_REG, patch 0007, cannot reach hardware).
Note: this patch is made against the tree that patches 0001-0007 produce (it touches src/util.c, which patch 0006 also changes).

Files: `src/3D140.c`, `src/util.c`, `src/stage_loader.c`


## 0009-geo-render-matrix-pointer-array.patch

Port patch 0009 - an array the decomp declared too small
Why: D_800AA6C8 in src/geo_render.c holds one matrix pointer per animated part. The decomp declares 8 entries and then a 0x1E0-byte
padding array (pad_D_800AA6E8); the true array is 0x200 bytes (128 entries). On the console the padding follows the array in memory,
so an index of 10 (which the model data really contains, found while running the game) is harmless. In this port the compiler places
statics in any order, and index 10 overwrote the neighbouring pointer D_800ABCB8 (found with a hardware watchpoint). The array is
declared at its true size and the padding array is removed.

Files: `src/geo_render.c`


## 0010-model-accessors-null-object.patch

Port patch 0010 - model accessors that read low memory when no object is being drawn
Why: ModelRenderer_GetActiveMode / GetObjectType (src/battle_hud.c) read fields of the display object D_8006F09C. It is NULL except
while an object is drawn, and the callbacks of a geo layout run once when the layout is built (GeoNode_SetCallback calls
callback(0, node)), before any drawing. The console then reads a small offset of segment 0 (0xA6 for GetActiveMode), which maps to the start of
RDRAM (Memmap_SetSegmentMap(0, 0x80000000, osMemSize), src/stage_loader.c): memory that holds no game data. This port gives game
code no memory at such low addresses, so the read crashed (found by running the game). The value is not used in the cases that reach it
(the callback only uses it when its first argument is 2), so both accessors return 0 for NULL.

Files: `src/battle_hud.c`


## 0011-report-relocated-fragments.patch

Port patch 0011 - report every relocated fragment to the host
Why: the port runs the C code of the code overlays natively and maps a call into a loaded overlay to the native function
(src/platform/host_fragment.c). It found the overlay through gFragments, but that table keeps ONE entry per id: the battle scene loads

Files: `src/memmap.c`


## 0012-jpeg-task-statics.patch

Port patch 0012 - keep the JPEG task's parameter block and quantisation tables out of the thread stack
Why: Jpeg_DecodeImage passes the address of a local parameter block (sp90) to the RSP task and stores the addresses of two local
quantisation tables in it after reducing them with '& 0x1FFFFFFF' (virtual to physical address). On the port a thread's stack is host
memory outside the low address range in which a pointer is the physical address, so those addresses were mangled and the host-side
JPEG decoder (src/render/jpeg_task.c) crashed reading them (found by running the game). Making both static puts them in the program
image, which lies below 0x01000000. The decoder is not reentrant anyway (Jpeg_DecodeMcus keeps its bit-stream state in globals).

Files: `src/jpeg_stream.c`


## 0013-font-glyph-table.patch

Port patch 0013 - look up font glyph indices in the glyph table by name
Why: Font_MapGlyphCode reads the glyph table D_8006F650 only by indexing past the end of the display-list arrays gUiRestoreTextureDL
(code 0x20..0x7F) and D_8006F608 (code 0xA0..0xFF), relying on the original linker placing the table right behind them. Nothing else

running the game, confirmed with nm). The table is now non-static and indexed directly with the same indices as the original layout
(code - 0x20, and 0x60 + code - 0xA0; the US table has 0xC0 entries). Behaviour on the original build is unchanged.

Files: `src/ui_graphics.c`, `src/graphics_textures.c`

## 0015-missing-returns.patch

Port patch 0015 - return the value the console leaves in register v0 where the decomp has no `return`
Why: 35 non-void functions of the decomp run off their end (clang: -Wreturn-type). On the console the caller sees what is left in
v0; in clang's output the result is an undefined value. tools/native/be_memory.py (rule 6) makes every such path return 0, which is
right for functions whose result nobody reads. The functions below are read by their callers, so they get an explicit return:
  - Audio_DispatchSoundBankCommand, Audio_PlayDirectSoundCommand, Audio_PlayCategory11SoundCommand, Audio_PlayCategory12SoundCommand:
    each ends with `D_80079018 = x;` and the console returns that same x (still in v0). Without it the sound handle was lost, the
    game could never stop looping sound effects, and a later sound-bank swap left a running effect reading another bank's bytes (found
    by running the game: crash in the audio thread after the rental screen).
  - Gallery_GetCommonUiString / Gallery_CopyCommonUiString: return the result of their Text_GetString call (still in v0).
  - Effect_TriggerMoveVisual: returns `ret`, the handle of the sound it just started. NOT VERIFIED against the console code: the
    decomp has no return, so the original value cannot be read from it; the callers store it as the sound handle, so this is the only
    sensible value.

Files: `src/audio_commands_category2.c`, `src/audio_fade.c`, `src/fragments/gallery_backgrounds/gallery_backgrounds_2A3E70.c`


## 0016-uninitialised-ptr-ai.patch

Port patch 0016 - do not read through an uninitialised pointer in BattleAI_SelectBestScoredMove
Why: the function contains `sp70 = ptr->unk_57 * 0;` while the local `ptr` has not been assigned yet (`ptr = &arg0->unk_12;` comes
a few lines later). The product is always 0 - it is a leftover of the matching process of the decomp. On the console the stale
register presumably points somewhere readable and the result is thrown away (not checked on hardware); in the native build the pointer is whatever the stack held and the read
crashed the game now and then, while the computer player chose a move (found by running the game: SIGSEGV, ptr == NULL, core file
analysed with gdb). The patch assigns the value that expression always has, 0. No behaviour of the original changes.

Files: `src/fragments/battle_engine/battle_engine_361050.c`


## 0017-battle-tick-slot-spare.patch

Port patch 0017 - give the battle-scene tick-slot array the spare slot that the console's memory layout provided
Why: the "tick" callbacks of the battle animation state machine retire themselves with `slots[sBattleSceneStateTickSlotIndex].callback = sentinel`.
The index is the loop counter of BattleScene_TickStateCallbacks, which stays 7 after the loop. Some callback evidently runs with the counter at 7
(which path does that was NOT traced) and then writes slot 7, one past the array of 7. The decomp's symbol table shows what
the console had there: the array ends at 0x843900A0, then sBattleSceneStateTickSlotIndex (0xA0) and D_843900A4, a variable that nothing
reads, so the stray write was harmless. In the native program the linker places other variables behind the array; found by playing a
battle for several minutes: sActivePokemon[1] became the address of BattleScene_StateCallbackNop and the next tick crashed. The patch makes
the array 8 long (the loops still run to 7), so the stray write has a place to go. This is the third case of a console memory layout being
relied on by accident (see also the aliases for gBaseStats and D_800780B3 in tools/native/gen_platform_symbols.py).

Files: `src/fragments/battle_engine/battle_engine_move_animation.c`


## 0018-gb-emulator-buffer-array.patch

Port patch 0018 - the Game Boy emulator's buffer-pointer array really has three entries (the third is the variable the decomp calls D_8122B2E0)
Why: GB Tower emulator start (func_812033F4) stores three buffer pointers with `((u8**)D_8122B2D8)[i] = ...` for i = 0..2 and later code reads
the third one as `D_8122B2E0`. The decomp declares D_8122B2D8 with 2 entries and D_8122B2E0 as a separate s32; on the console they are adjacent
(D_8122B2D8 + 8 == D_8122B2E0; the variable names are the console addresses and the symbol_addrs of the de, us_rev1 and us_rev2 versions agree), so the "out of bounds" store of entry 2 is the store to D_8122B2E0. In the native program the linker puts the
variables in another order and the store landed on D_8122B2C0, the pointer to the emulator state: later code then used a pixel buffer as the
emulator state (seen: the thread waiting for a flag that is never cleared, the flag byte full of picture data). The patch declares the array with
3 entries and defines D_8122B2E0 as a name for the third (it is only ever read). This is the fourth case of the console's memory layout being
relied on by accident (see patch 0017).

Files: `src/fragments/gb_tower_emulator/gb_tower_emulator_7F9A0.c`


## 0019-pool-pop-left-walk-bound.patch

Port patch 0019 - main_pool_pop_state ends its left-side walk at a link that is not inside the pool
Why: leaving the Game Boy Tower (GbTower_Stop -> main_pool_pop_state('GBEM')) crashed. The emulator start (func_812033F4) DMAs the compressed
"misc" table (ROM 0xADC80..0xF4130, 0x464B0 bytes) to the heap address + 0x80000, which is 0x146A8 (83,624) bytes past the end of its 0x1FEAF0-byte pool
allocation, so the pool's left head block (the 16 bytes after the allocation) is overwritten with ROM bytes: its `prev` becomes 0x654D2A32. The decomp
has the same layout on the console (the staging area is temporary and the free pool space after it is not otherwise used), and there the left
walk `while (listHeadL <= argptr)` ends at once, because 0x654D2A32 is below every 0x80xxxxxx address. In the native program all addresses are below
0x01000000, the comparison is true, and the walk dereferenced the garbage. The patch adds a "link is inside the pool" test to the loop, which
gives the same result as the console for this case (no left-side block function runs at that pop - an inference from the code and the ROM bytes,
not observed on a console) and changes nothing for an intact chain. Fixing the overrun instead would run those block functions for the first
time, which is a behaviour change the console never had. See docs/known-decomp-issues.md ("address-space accident").

Files: `src/memory_main.c`


## 0020-gb-cart-title-table.patch

Port patch 0020 - the Game Boy cartridge title check no longer depends on four variables being adjacent in memory
Why: with a Game Boy cartridge inserted the Transfer Pak flow ended in "The Transfer Pak is not set properly": GbPak_DetectSupportedCartridgeVariant returned 0

## 0021-gb-audio-stream-table.patch

Port patch 0021 - make the GB Tower sound-effect stream table a real pointer table
Why: GB Tower plays short sampled sound effects through func_81209374, which looks the sample data up in a table (D_81228654, nine entries).
The decomp holds that table as a byte array whose bytes are the console's link-time addresses of the sample arrays (0x8120EB94 and so on). That
works on the console only because the console linker placed the arrays at exactly those addresses. In the native program the arrays are
elsewhere, so the first sound effect (found by pressing B and then C-Up in Pokemon Red inside GB Tower) made the player read from 0x8122864C
and crash with a segmentation fault. The patch writes the table as pointers to the arrays by name, in the original order.
The original numbers were checked before rewriting: entries 0 and 1 are the 8-byte zero array D_8122864C, entries 2..8 are seven chunks of one
sample area whose sizes (table D_81228678) added to each address give the next address (0x8120EB94 + 0x6B40 = 0x812156D4, and so on), so the entry
-> array assignment is not a guess. The table keeps its size on a 32-bit build (9 x 4 = 0x24 bytes).
This is the sixth case of the program relying on the console's link layout (see 0017, 0018, 0020 and the aliases in tools/native/gen_platform_symbols.py);
it is the first one where the layout was baked into DATA as raw address bytes. Other data tables of that kind may exist: a search for byte
tables that look like address lists found none in a first pass (the search was a rough pattern and is NOT exhaustive).

Files: `src/fragments/gb_tower_emulator/gb_tower_emulator_86CB0.c`


## 0022-gb-color-ucode-contiguous.patch

Port patch 0022 - keep the Game Boy Color RSP program and its constants back to back
Why: Pokemon Yellow is a Game Boy Color cartridge (header byte 0x143 has bit 7 set), so GB Tower runs it with the colour RSP program D_812297C0.
The program (633 words, 0x9E4 bytes) does not carry its constants: at IMEM 0x074 it DMAs 0xB0 bytes into DMEM from "ucode_boot + 0x9F0" (the
word at DMEM 0xFC8 is the ucode_boot pointer). On the console the linker puts the constants array D_8122A1A4 directly after the program (the
decomp even computes the program size as D_8122A1A4 - D_812297C0 = 0x9E4), so ucode_boot + 0x9F0 is the first non-zero constant (0x01010202;
the array starts with three zero words).
A native linker aligns each array to 8 bytes, so D_8122A1A4 sat at +0x9E8 and the program read its constants 4 bytes too early: all colour masks and
shift factors were wrong, and Yellow's picture came out as raw colour values (flat blue, striped olive sprites).
The patch makes the program and the constants ONE array (633 + 47 words, no gap) and keeps the name D_8122A1A4 as a macro for the start of the
constants, so the size calculation still gives 0x9E4. The black-and-white program (D_8122A260, 0xA40 bytes, constants read at + 0xA40) needs no
change because 0xA40 is a multiple of 8; that is why Red and Blue were never affected.
How it was found: the dumped program was disassembled by hand (tools: a small RSP decoder in the session scratch area); the DMA source offset 0x9F0
and the 0x9E4 + 12 relation were compared with the addresses in the built program (D_8122A1A4 - D_812297C0 = 0x9E8 there).
This is the seventh case of the program relying on the console's link layout (see 0017, 0018, 0020, 0021 and the aliases in
tools/native/gen_platform_symbols.py); it is a layout assumption made by RSP code, not by the C code.

Files: `src/fragments/gb_tower_emulator/gb_tower_emulator_7F9A0.c`


## 0023-move-table-contiguous.patch

Port patch 0023 - the move table (D_800780B4) is one table, keep its three parts back to back
Why: src/3D140_2.c holds a table of 165 three-byte move entries (effect, power, category) and the decomp splits it into three arrays: D_800780B4 (204 bytes),
D_80078180 (96 bytes) and D_800781E0 (196 bytes). The code does not care about the split: `moveEntry = &D_800780B4[(moveId * 3) - 3]` runs up to move 165
(0xA5; the function rejects 0xA6 and above) and 3D140.c reads the same table as D_800780B3[n * 3]. That works on the console because its linker put the
three arrays back to back (0x800780B4 + 204 = 0x80078180, + 96 = 0x800781E0). A native linker aligns every array to 8 bytes (tools/native/ir_sizes.py,
raise_alignment, needed for DMA'd tables), so 4 bytes of padding were inserted after the 204-byte array and every move from number 69 on was read 4 bytes
off (wrong effect, power and category for those moves).
The patch makes the three parts ONE array of 496 bytes (495 bytes of table for 165 moves and one spare byte) with no gap. D_80078180 and D_800781E0 were
not referred to by name anywhere in the decomp (checked with grep), so no alias is needed; the existing alias D_800780B3 = D_800780B4 - 1 is unchanged.
How it was found: the array-bounds checking build (docs/known-decomp-issues.md, "Array-bounds checking") reported an index of 258 into the 204-byte array at
3D140_2.c:2590 during a long scripted battle. Then the native addresses were compared with the console's: nm shows D_80078180 at D_800780B4 + 0xD0, the
console at + 0xCC. Move 69's entry begins exactly at the start of D_80078180 (204 = 68 * 3) and move 100's at the start of D_800781E0 (300 = 100 * 3), which
supports the reading that these are one table.
Consequence: the damage/effect estimate in that function now sees the right data for moves 69..165. What it feeds (the function around 3D140_2.c:2560) was
not traced in full; the patch fixes the data, it does not claim to have observed a changed battle.
Eighth case of the program relying on the console's link layout (see 0017, 0018, 0020, 0021, 0022 and the aliases in tools/native/gen_platform_symbols.py).

Files: `src/3D140_2.c`


## 0024-gb-apu-regs-bitfields.patch

Port patch 0024 - read the Game Boy sound registers with shifts and masks instead of C bit-fields
Why: the Game Boy Tower (Transfer Pak emulator) was SILENT natively. The emulator keeps the Game Boy sound registers NR10..NR52 in the byte array
D_8120EA70 and the decomp reads them through a struct of bit-fields (GbApuRegs, GB_APU_REGS.power and so on). The MIPS compiler puts the first
declared bit-field in the most significant bits of a byte, the x86 compilers in the least significant, so every field read the wrong bits. In
particular ".power" (bit 7 of NR52) read bit 0, which is 0 after the game's own register writes, and func_8120806C then ignored every sound
register write because it believed the sound hardware was off. Measured on Linux: register writes with real values reached func_8120806C, yet
every buffer passed to osGbSetNextBuffer was all zeros.
The patch replaces the struct with one accessor macro per field (shift and mask on the byte that holds it). The positions come from clang's
record layout of the ORIGINAL struct for MIPS o32 big-endian and match the documented Game Boy register layout (see the comment in the patch).
All 68 uses in the file were reads, so only reading macros exist. This patch applies on top of 0021 (same file). The file no longer needs an
entry in port/bitfield_known.txt (the build refuses bit-fields in files that are not listed).
Not checked: the sound itself has still not been LISTENED to; only that the synthesised buffers are no longer silent (see docs/test-checklist.md).

Files: `src/fragments/gb_tower_emulator/gb_tower_emulator_86CB0.c`


## 0025-gfx-idle-before-pool-reuse.patch

Port patch 0025 - wait for the graphics task before the main pool gives memory back (main_pool_free, main_pool_pop_state)
Why: the console's RDP draws a frame in well under a field, so by the time the game frees the memory of the last scene (main_pool_free / main_pool_pop_state, at a scene change)
the last frame's display lists, textures and vertices have long been drawn. The native software renderer runs as a task on a worker thread and a frame can take two fields or
more; if the game frees and re-uses that memory (the new scene's data is loaded into it) while the drawing still reads it, the task calls a sub-list that is already overwritten
(0xFFFFFFFF words) and draws garbage or crashes (measured with the "wait only when drawing into the shown buffer" experiment).
__osHostGfxIdleBeforeReuse (src/ultra/hw_sp.c) returns at once when no graphics task runs, otherwise it finishes the running task. Memory is only handed out again after a free,
so this one place covers every reuse of pool memory without stopping the game at every field (the older fix, waiting at every picture change, made the whole game stand still for
a full drawing task each field and starved the audio thread).
Not covered: data at fixed addresses (overlay code and data are loaded to fixed places); see docs/windows-test-guide.md / the performance notes if this ever shows up.

Files: `src/memory_main.c`


## 0026-debug-knockout-cheat.patch

Port patch 0026 - debug cheat: L+R knocks out the opponent's Pokemon (L+R+Z wins the battle)
Why: a requested quality-of-life/debug feature of the port. It is carried out inside the game's own battle code, not by the host poking at memory from outside, so that the game's
normal faint sequence plays and its state machine stays consistent.
How: Port_WatchKnockoutChord (battle_engine_main.c, called at the start of every battle frame, BattleScene_UpdateFrame) looks at the first player's controller:
L and R both held and any of L, R, Z newly pressed arms the cheat, whatever the order the buttons went down in (Z held as well: the "win" variant; a knock-out that is already armed is upgraded when Z joins, never downgraded). The cheat is carried out in Battle_ResolveMonAction
(battle_engine_359F90.c) right after the turn's calculation and before the game's own faint check (Battle_CheckFaintAfterMove): the opponent's active Pokemon gets
current HP 0 (BattleMonRuntime.unk_0C; the HP shown on screen follows it through BattleScene_AnimateDisplayedHpToRuntime) and, for the "win" variant, every other
Pokemon the opponent brought gets HP 0 in the roster (BattleMon.unk_02), which the Battle_CheckAllBroughtFainted_* functions add up. So after the NEXT turn resolves
(the player picks a move as usual) the opponent faints with the normal animation. When no HP animation is pending (the shown HP BattleMon.unk_02 equals the real HP, which is the case after a move that missed, failed or did no damage) the shown HP and its float tracker D_843900A8 are set to 0 too: after such a move the game calls BattleScene_AnimateDisplayedHpToRuntime only once per presentation round (about 50 frames), a step of max HP / 90 each, so the bar would otherwise need over a minute (reported by the user: "drains incredibly slowly" after a miss or a failed effect). After a damaging move the scene animates every frame and the cheat leaves the shown HP alone. It is not applied in the middle of a menu: the state machine of the turn playback is not
meant to be interrupted there.
The opponent is the side whose active Pokemon is not controlled by gPlayer1Controller (state.unk_C8). The host decides whether the cheat is on (__osHostCheatsEnabled:
settings menu / config file, default on) and gets notices (__osHostCheatNotice) to show a message on screen and write the log.
The armed state (sPortCheatPending) is an overlay variable: it starts at zero whenever the battle overlay is loaded, so a cheat armed in one battle cannot fire in the next.
Meaning of the fields was taken from reading the decomp (unk_0C = current HP: BattleScene_AnimateDisplayedHpToRuntime, D_843900A8; unk_28 = maximum HP) and is checked by a

## 0035-pool-alloc-gpu-invalidate.patch
